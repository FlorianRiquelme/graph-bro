Issue #10 offered three output targets for a reviewable topology picture: a Mermaid flowchart, Graphviz DOT, or a self-contained interactive HTML inspector. The third is chosen, so this set does not re-argue the target. It ideates inside the inspector: what it draws, how it behaves, how it is built, and what to decide now so the deferred run overlay is an extension rather than a rewrite.

Grounding Context

Codebase Context

graph-bro is a TypeScript workflow-orchestration engine that runs graphs of CLI coding-agent nodes with loops, fan-out, and joins, checkpointed for crash-safe resume. Runtime dependencies are exactly two — better-sqlite3 and zod — and there is no bundler in the project at all; build is a bare tsc, with a postbuild that shell-copies .sql migrations into dist/. CLI verb dispatch is a plain switch on process.argv[2] with no CLI framework, and every existing verb emits JSON or NDJSON to stdout. There is no HTML anywhere in the repo today, and CI is only npm ci → build → test.

What the renderer would be fed

compile() already splits the three edge shapes into separate arrays — plainEdges, fanOutEdges, joinBarriers — so the grammar's three-way distinction is pre-made. Each JoinBarrier already carries a synthesized id of the form `${from.join(",")}=>${to}`, which is exactly what a join-drawn-as-a-node needs.

Two facts constrain the renderer's signature. Lint warnings live on CompileResult, not inside CompiledTopology, so a pure function that draws lint on the offending join needs both halves. And lint.ts sets join: join.to — the join's target node id, not the JoinBarrier.id — so warning-to-join matching is ambiguous when two joins share a target.

What is deliberately unknowable at author time

Fan-out N is known only at run time (R3). START and END are sentinel ids, not declared Node objects, so the renderer must synthesize them. And when guards are used only for compile-time lint analysis in slice 1 — conditional routing execution is deferred (KTD-7) — so a map that draws a when label as though it routes is asserting something the engine does not do.

A topology may loop and is explicitly not a DAG. The only bound is a single global max_steps; the frontier is recomputed dynamically each super-step, and there is no pre-computed topological rank or level anywhere in the codebase, so any layered layout has to invent ranks itself.

The reader tension

STRATEGY.md's observability track names an agent (Opus/Fable session) as the primary reader of run history, and ADR-0003 keeps the CLI as the legibility layer — "the agent reads CLI output, never SQL." The topology map's reader, by contrast, is a human. The inspector is the first artifact in the repo where those two readers meet.

External landscape

Argo Workflows shipped a "preview graph before submitting" feature for exactly this need, and its dynamic withItems counts remain a known UX gap — so static unknown-N rendering is poorly solved elsewhere, not a solved problem. AWS Step Functions draws its Map state as a single collapsed boundary regardless of actual N. BPMN's multi-instance marker (three bars; vertical = parallel, horizontal = sequential) is the established notation for "this becomes N at run time," and the Petri-net / workflow-patterns literature already names graph-bro's resettable barrier a Generalized AND-Join. LangGraph Studio is server-backed with no offline single-file mode, so the "opens as a file, no server" angle is genuinely differentiated. For layout, elkjs has mature built-in cycle-breaking (GreedyCycleBreaker + ReversedEdgeRestorer) but is heavy and async; lighter Sugiyama libraries need a feedback-arc-set pre-pass.

The one fork this set does not resolve

How cycles are handled is the ticket's largest irreversible decision, and it cascades into the dependency choice, the bundle size, whether a no-JS build is viable, and the snapshot strategy. Four rival answers surfaced — strongly-connected-component condensation into rings, music-notation-style symbolic jump marks, hand-rolling the cycle-breaker over a light library, or adopting elkjs behind a seam. Survivor 4 changes what the ranks mean either way, but the engine choice itself should be made deliberately rather than backed into.

1

Name the TopologyMapModel — one object, five jobs

axis: build-and-distribution confidence: 88% complexity: Medium

Description

Split the renderer into two pure functions rather than one: CompiledTopology + warnings → TopologyMapModel, then TopologyMapModel → HTML. The middle object is a zod-defined description of the drawing's meaning — node boxes, edge classes, badges, labels, ranks, warning attachments — and it is deliberately given a name and a schema instead of existing as anonymous intermediate state.

Naming it collapses five otherwise-separate design problems into one. It is the snapshot-test target, so a layout-library bump or a CSS tweak churns no fixtures and every grammar decision is reviewable as text in a diff. It is the machine-readable payload embedded in the emitted file, so an agent can read the HTML and answer questions about the topology without a browser. Its order-normalised serialization is a semantic digest, which makes "what did this PR change about the topology's meaning?" a readable diff rather than two pictures to compare. It is the extension point the deferred run overlay attaches to. And its node and join keys — reusing compile()'s own already-synthesized ids — become the stable DOM ids, so the overlay never has to invent a second scheme for matching trace events to elements.

Basis

direct: ADR-0001 states that "zod-everywhere now binds: topology grammar, run-trace schema, and CLI-agent JSON contracts all zod-defined, not just HTTP-edge validation" — so a zod-defined render model is the house pattern, not a new one. compile.ts already synthesizes JoinBarrier.id as `${from.join(",")}=>${to}`, and deriveInstanceId(nodeId, itemKey) already produces `${nodeId}:${itemKey}`, so the id scheme exists and matches the trace's own vocabulary (Activation carries nodeId and instanceId). The existing test/topology/__snapshots__/compile.test.ts.snap is the snapshot convention to follow.

external: Playwright's HTML reporter inlines its assets and data by default, with a doNotInlineAssets escape hatch for strict-CSP environments — precedent for an embedded payload inside a single self-contained report. (Note: Playwright's separate trace viewer is not precedent here — it requires a registered service worker and cannot be a single file.)

reasoned: A snapshot of a laid-out HTML document is the worst available snapshot target: unreadable in review and invalidated by every cosmetic change, which trains the team to stop trusting snapshot diffs. Splitting the pure function is what makes the snapshot meaningful, and once the intermediate object exists and is serializable, the other four jobs are nearly free consequences rather than separate features.

Rationale

Every other survivor here touches this object. It is the cheapest decision in the set to make correctly and the most expensive to retrofit, because it is the one that determines whether the deferred overlay ticket populates a field or redesigns a renderer. It also resolves the human-versus-agent reader tension without a second output target: the SVG is the human channel and the embedded model is the agent channel, honouring ADR-0003's "CLI is the legibility layer" doctrine rather than contradicting it with the repo's first non-JSON artifact.

Downsides

It is more structure than the minimum that draws a picture, and the author's own conventions warn against speculative abstraction. The defence is that four of the five jobs are real today (snapshot, payload, digest, DOM ids) — only the overlay hook is future-facing, and survivor 3 covers that without unpopulated fields. There is also a genuine question of how much of the visual decision belongs in the model versus the template; drawn too wide, the model becomes a second CSS.

2

The inspector needs no JavaScript

axis: interaction confidence: 65% complexity: Low

Description

Take the interaction inventory literally. Everything issue #10 asks for is disclosure: expand a node to see its full prompt template, expand an edge to see its for_each path or its nested when rule, expand a warning to read its message. Disclosure is the one interaction HTML has natively. So build the inspector as inline SVG for the graph plus <details>/<summary> for every panel, with #node-reader-style URL fragments and :target CSS for focus — and ship zero runtime JavaScript.

The unexpected payoff is citability. Every node, edge, and join gets a stable, quotable address. A PR comment can link to this join instead of describing it, and so can an agent. Pan, zoom, and search — the things that would need JavaScript — are replaceable by browser scroll and Ctrl-F, which is also what makes the file's text searchable by an agent reading it as source.

Basis

reasoned: Enumerate what the inspector must let a reviewer do, from the issue's own list: read a prompt template (long text, needs hiding by default), read a recursive when rule tree (unbounded depth, needs progressive expansion), read a lint message, see a model and an output_key. Every one is show/hide. Nothing in that list requires state, computation, or a layout recomputation in the browser — the layout is computed once, at render time, by the CLI. The conclusion follows: the runtime is unnecessary, and the only reason to add one would be features not asked for.

direct: This is the decision that resolves the build problem rather than working around it. The repo has exactly two runtime dependencies and no bundler at all — build is a bare tsc plus a cp for migrations. No JavaScript in the artifact means no bundler needs to be introduced.

external: Metaflow Cards require render() to return one self-contained HTML string with no external file references (images as data URIs), which is the same constraint treated as load-bearing in a comparable orchestration ecosystem. Playwright's doNotInlineAssets exists precisely because strict-CSP environments are a real deployment target for report files.

Rationale

The tension the grounding surfaces most sharply is between the author's "rely on the broad, mature ecosystem" convention and the fact that a mature in-browser layout engine is a heavy async dependency inside a file that is supposed to be self-contained and diffable. This idea dissolves rather than resolves that tension: the layout runs in Node at render time, where using a mature library costs nothing at distribution, and the artifact stays a document. It also makes the file robust in the places single-file reports actually get opened — email attachments, sandboxed viewers, strict CSP, an agent's HTML-to-text pass.

Downsides

This is a hard architectural fork, and it is the reason confidence is only moderate: it forecloses interactions that might turn out to matter for a large topology — collapse/expand of subgraph groups that changes layout, drag-to-explore, live filtering. Issue #10 explicitly imagines "collapse/expand," and a purely CSS collapse cannot reflow the graph, only hide detail panels. If large topologies later demand real navigation, this decision gets revisited, and revisiting it means introducing the bundler this idea avoided.

3

Mimic-panel invariance: the overlay may only paint

axis: growth-path confidence: 90% complexity: Low

Description

Commit now, as a tested invariant, that layout geometry is a pure function of compile-time facts and never consults run data. The deferred run overlay is then restricted to painting: fills, badges, and pre-reserved text slots. One test asserts that the layout output is byte-identical with and without overlay data present.

The slots are already knowable from the code that exists: the fan-out marker takes the real N, node fills take the four run statuses, and a join node takes arrived-versus-expected counts. Naming them now is a line of schema, not a feature.

Basis

external: Railway interlocking and SCADA mimic panels use one track schematic for two jobs — the engineer reviews it before commissioning, and the same geometry is the illuminated panel during operation. That dual role works only because the geometry is fixed and only the illumination changes, which is what preserves the operator's spatial memory. Metaflow documents the same split in software, between static cards and render_runtime/refresh variants.

direct: The overlay's data already exists in the shapes this invariant needs. CheckpointSnapshot carries frontier: Activation[] with per-instance itemKeys — precisely the "which N branches exist right now" information. Run statuses are running | completed | dead_end | failed; note that dead_end has no visual convention yet and will need one.

reasoned: If layout may ever consult trace data, then the pre-flight map and the live map disagree in position, and the reviewer's memory of "the join is bottom-right" becomes a liability rather than an asset. That divergence is exactly the rewrite the growth-path concern exists to prevent, and it is unrecoverable once the overlay ships against a layout that moves.

Rationale

The run overlay is deferred to its own ticket, which means this ticket gets to decide, for free, whether that ticket is an extension or a rewrite. The entire cost is one stated invariant and one test. It is also the non-speculative answer to the growth-path question: it constrains the future without adding unpopulated fields to the present, which is what the author's "no unrequested configurability" convention would otherwise object to.

Downsides

It forecloses overlay designs that might genuinely want to reflow — for instance, expanding one authored fan-out node into its real N instances side by side once N is known. That is a plausible thing to want, and this invariant rules it out or forces it into a second, separate view. The invariant is also only as strong as the test that enforces it.

4

The y-axis means super-step

axis: layout-and-loops confidence: 82% complexity: Medium

Description

Rank nodes by earliest possible super-step — breadth-first from START over plain and fan-out edges, with barriers gated on their sources — and make the vertical axis mean that. Row one is the first frontier, row two the second. Draw max_steps as the ladder's declared height, so the budget is a visible scale rather than a caption. A loop then reads as an edge pointing back up the ladder against a bound you can see.

Basis

direct: CONTEXT.md defines the super-step as the engine's own execution unit — "snapshot state, run the ready frontier, merge updates through reducers, recompute the next frontier, checkpoint." src/engine/loop.ts's transition() computes the next frontier dynamically each step by walking completed-node adjacencies, and there is no pre-computed topological rank or level anywhere in the codebase. max_steps is a required positive integer, so the bound always exists to draw.

reasoned: The choice is not whether to have ranks — every layered layout invents them — but whether they mean anything. Meaningless ranks are an artifact of the algorithm; super-step ranks make the vertical axis answer two questions a reviewer actually has: how many rounds is this, and how much of my max_steps budget does one loop iteration consume? Neither Mermaid nor DOT answers either, which is part of why the cheap text targets are "just fine."

Rationale

This is the idea that makes the picture say something the JSON does not. It also composes with survivor 3 at no cost: if rows are super-steps, then a checkpoint's step maps directly to a row, so the deferred overlay's most natural affordance — showing where a run currently is — is a row highlight rather than new layout logic.

Downsides

"Earliest possible super-step" is a static approximation of something genuinely dynamic. Conditional routing and data-dependent fan-out mean the real schedule can differ from the drawn one, so the ladder is a lower bound, not a prediction — and it must be drawn in a register that admits this (survivor 5). It also constrains layout: a wide graph with few steps becomes short and very wide, which may read worse than a conventional layered layout for some topologies.

5

One ink register for everything the compiler cannot know

axis: visual-grammar confidence: 80% complexity: Medium

Description

Instead of inventing a separate badge for each thing the compiler cannot know, define a single systematic register: everything the compiler actually asserts draws solid, and everything conjectural draws in one consistently-defined "unsurveyed" treatment. The register is enumerable from the code today — fan-out N, the synthesized START/END sentinels, the approximate super-step ranks from survivor 4, and, sharpest of all, when guards.

That last one is a lie the map would otherwise tell. when is used only for compile-time lint analysis in slice 1; conditional routing execution is deferred. A map that draws a when label as a normal edge label asserts that the engine branches on it, which it does not. Under a register, that edge is drawn as unsurveyed and the picture stays honest.

Basis

external: Nautical charts do not badge uncertainty per feature; they carry a register. Surveyed coastline is solid, unsurveyed shore is hachured, and IHO qualifiers (PA position approximate, ED existence doubtful, plus CATZOC zones of confidence) let a mariner read survey confidence from the ink itself. The ICOMOS Venice Charter's Article 12 encodes the same principle in a different medium: restoration material must remain visually distinguishable from surviving original fabric.

direct: src/topology/schema.ts states that the when DSL is "used only for compile-time lint analysis in slice 1 (conditional routing execution is deferred, KTD-7)," and that START/END are "not declared as Node objects — only referenced from from/to." Fan-out N is known only at run time (R3). Three separate grammar problems, one property.

Rationale

Issue #10 treats unknown N, the sentinels, and when labels as separate drawing decisions, each inviting its own badge. They are one problem with one answer, and naming the register up front means the deferred run overlay has an exact job description: survey the unsurveyed parts. It also catches a lie nobody flagged — slice 1 would happily draw when labels on edges the engine does not branch on.

Downsides

A register is only legible if it is small; adding a third tier ("known but approximate" for the super-step ranks) starts to erode the binary that makes it readable at a glance. There is also a real argument that when should simply not be drawn at all in slice 1 rather than drawn hedged, and someone will make it. That is a legitimate alternative this idea should be weighed against rather than assumed past.

6

Draw the provenance the new lint computes and throws away

axis: interaction confidence: 85% complexity: Low

Description

The prompt-token lint that landed mid-run computes exactly the right set and then discards its most useful half. collectStateRootKeys gathers every root key the run can produce — from set update keys, agent output_keys, fan-out as bindings, join into keys, and the --input snapshot — and checkPromptTokens then reduces all of it to a yes/no membership test per token.

The inspector should keep the association it throws away: for each interpolation token in each prompt template, draw which node produces that root key. A token becomes a link to its producer. Two things the lint deliberately cannot do then come free from the drawing. The lint is root-keys-only and flat by design, so dotted depth goes unchecked — but the panel can show the token's full path next to the producer's declared key, making a depth mismatch visible to a human. More importantly, the lint is whole-topology and not per-node: a key produced anywhere counts everywhere, which the code itself calls "the cheap half of the check," explicitly ruling out the "what keys exist at node X" reachability analysis as oversized. A picture answers reachability by eye — you can simply see whether the producer is upstream of the consumer, or off in a branch that never runs first.

Basis

direct: src/topology/lint.ts, as of ef37b53, documents both limits in its own comments. On flatness: "Root keys only, and deliberately flat… Enumerating roots is therefore exact, while anything deeper is a runtime fact." On reachability: "Whole-topology, not per-node reachability — a key produced anywhere counts everywhere. That is the cheap half of the check: it catches typos without the 'what keys exist at node X' analysis the issue rules out as oversized." collectStateRootKeys builds the producing set and checkPromptTokens reduces it to known.has(root), discarding which node contributed each key.

reasoned: The expensive part of per-node reachability analysis is presenting it, not computing it — and a laid-out graph is the presentation. Once nodes are ranked (survivor 4), "is the producer upstream" is a comparison a human makes by looking, at zero analysis cost. So the drawing can deliver the check the lint explicitly declined to build, without building it.

external: A Baroque figured bass is a deliberately unrealized score — bass line plus numerals, resolved by the performer at performance time. What makes it workable is the strict rule that every figure must be realizable from the notated bass, so an unrealizable figure is an error catchable on the page. The same split exists here between prompt template and resolved prompt, and the same page-level check applies.

Rationale

This is the strongest evidence in the run that reading the code beats reasoning about it. Five of five ideation frames proposed adding a static token check; the check was already written and in review. Reading it revealed something better: the feature's own comments name two limits it accepted deliberately, and a picture relieves both. It also gives click-to-inspect a purpose beyond displaying prompt text — each token becomes a navigable link to its producer.

Downsides

Upstream-ness is genuinely subtle in a cyclic graph: a producer that is "downstream" on the first pass is perfectly reachable on the second iteration of a loop, so a naive reachability read would produce false alarms on exactly the topologies graph-bro exists to run. This must be presented as information for a human to judge, not as a warning — and getting that tone wrong makes it worse than absent. It also needs the token extraction to respect the new escape grammar from 862e36d, since escaped delimiters are text rather than tokens.

7

Fan-out draws as a boundary, not a marked edge

axis: visual-grammar confidence: 70% complexity: Medium

Description

Issue #10 commits to drawing fan-out as one target with a marked, labelled edge, precisely because drawing N copies statically would be a lie. Keep that commitment but strengthen the mark: wrap the fan-out target in a labelled, collapsible boundary carrying for_each batch.items · as item · ×N at run time, with BPMN multi-instance bars on the target inside it.

A boundary states "one authored node, N runtime instances," where a marked edge can only imply it. It also scales: on a large topology a marked edge into a single target is invisible, while a frame is not. And it is the natural attachment point for the real N when the overlay lands, and the natural collapse handle if large topologies ever need one.

Basis

external: AWS Step Functions Workflow Studio draws the Map state — including Distributed Map at 10,000-way fan-out — as a single collapsed sub-graph boundary regardless of actual N. That is the canonical answer to "one node, N unknown at design time": a container wrapping the iteration body. BPMN's multi-instance marker supplies the glyph — three bars, vertical for parallel instances, horizontal for sequential — which is the established notation readers may already know. Argo Workflows, by contrast, renders dynamic fan-out as named sibling nodes only once counts are known, and its unresolved-count rendering is an open UX gap, so this is a differentiated answer rather than a copied one.

direct: The fan-out edge carries exactly the two labels the frame needs: for_each (a dotted state path) and as (the per-branch binding). And the adjacency is mechanically derivable rather than authored — a join whose sources is a single element matching some fanOutEdge.to is a fan-out join, which the schema comment spells out: "a single-element array is valid: a dynamic fan-out reuses one node id for all N branches, so the join's static source list has size 1."

Rationale

This is the single most load-bearing grammar call in the ticket, because fan-out and join are the vocabulary's whole point — a map where they are plain arrows is worse than no map. It also removes an ambiguity a reviewer would otherwise have to resolve by squinting: whether a one-source join is really eating a fan-out. The compiler already has the answer.

Downsides

A boundary costs vertical and horizontal space, which works against survivor 4's ladder on a graph with many fan-outs, and nested boundaries (a fan-out inside a loop) could get visually crowded fast. It also competes with two other notations that surfaced — a repeat-unit bracket with the count's source as a subscript, and bare BPMN bars with no frame — and the bracket has a real argument in its favour, since it makes the count's binding part of the mark. Confidence is moderate because this is a genuine three-way design choice, not a settled one.
